### RgGen and PeakRDL compatibility

RgGen's optional SystemRDL plugin was inspected at `c2647adb817398aeedbc514fef383ecc408da266`. Its [README](https://github.com/rggen/rggen-systemrdl/blob/c2647adb817398aeedbc514fef383ecc408da266/README.md), [field converter](https://github.com/rggen/rggen-systemrdl/blob/c2647adb817398aeedbc514fef383ecc408da266/lib/rggen/systemrdl/converter/field.rb) and tests agree: RgGen uses hardware precedence; SystemRDL defaults to software precedence. Effective `sw` is rejected unless `ignore_precedence` is enabled. Explicit `precedence = hw` or an inherited `default precedence = hw` is accepted. The override ignores the input choice and generates hardware-precedence behavior, so it is not lossless semantic interchange.

The [mapping notes](https://github.com/rggen/rggen-systemrdl/blob/c2647adb817398aeedbc514fef383ecc408da266/notes/systemrdl_to_rggen_mapping.md) also document unsupported external registers/regfiles, reference-valued resets, user reset signals and property references. Memories reserve external address regions; memory contents are not generated. Access width follows RgGen configuration. These limits do not imply every SystemRDL design is incompatible.

PeakRDL instead uses [SystemRDL elaboration](https://peakrdl.readthedocs.io/en/latest/processing-input.html) and [packaged exporters](https://github.com/SystemRDL/PeakRDL/blob/dc4f779cc97d07519d475ff392a2b26f6a8373f2/peakrdl/pyproject.toml), with IP-XACT mapped into that model. Its [community page](https://peakrdl.readthedocs.io/en/latest/community.html) distinguishes optional extensions. The drafts were compared side by side: RgGen emphasizes varied authoring and field/protocol/writer customization; PeakRDL emphasizes a shared elaborated model and exporter ecosystem. Root activity contains no PeakRDL-regblock or other component counts.
