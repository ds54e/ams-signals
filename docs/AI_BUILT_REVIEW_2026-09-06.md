# AI-BUILT provenance review — 2026-09-06

This review covers **all 75 projects: 35 Analog and 40 Digital**, beginning at `4345198dda42819bb099e3bb7c98e593254057c4` on `main`, after the Digital expansion landed. **Current AI-BUILT** below means the value at that starting revision, not the result of this audit. There were **8**, including newly added Veryl as well as the earlier seven.

The complete decision matrix was authored and checked against that inventory **before changing catalog data**. It supersedes earlier AI-built judgments in the domain implementation notes and [Scope review](CATALOG_SCOPE_REVIEW.md); those remain historical records of their respective passes.

## Shared policy

**AI-BUILT: “Substantial, directly evidenced AI-assisted development provenance of the project itself.”**

**Runtime AI and AI-BUILT are independent.** A stage’s `ai` boolean records model participation in the user’s design workflow. `scope.aiBuilt: true` records how the software was built. Either can exist without the other. Public provenance remains **true or absent**, with no strength, confidence, tier, partial or “AI-assisted” field or badge.

The badge requires a notable implementation contribution, directly grounded in project/maintainer evidence. A clear creation account or an explicitly documented substantial implementation campaign can qualify. A subsystem can qualify only when its evidenced AI-assisted implementation is substantial, current, architecturally important or user-facing, and significant enough to characterize the cataloged project. An existing feature’s importance alone does not establish how much of it an agent implemented. Forks and enhancement efforts are judged as the named project, without relabeling their upstream dependencies.

Runtime models, AI research subject matter, generated test inputs/examples, generated documentation, dependency updates, a bot PR, an instruction file or an isolated feature do not suffice. Commit credits support research but do not by themselves specify who designed/wrote which portions. A sustained credit pattern merits investigation; it is not converted into a code-authorship percentage or an automatic badge. Ambiguous cases remain unlabeled.

## Evidence tiers and method

- **A — Strong direct evidence:** project/maintainer explicitly documents substantial AI-assisted implementation. Public badge normally requires A.
- **B — Meaningful but bounded evidence:** a significant subsystem/campaign or sustained implementation assistance is visible, but the project-level attribution remains debatable. Default: no badge. No B exception is used in this audit.
- **C — Incidental evidence:** limited coding, maintenance, tests, documentation or contributor-tool use.
- **D — No credible public evidence found:** a bounded search result, not proof that no AI was ever used or that all code is human-written.

Reopened the eight existing labels first, then reviewed all 67 unmarked entries. Read catalog descriptions/notes, current canonical repository READMEs and available contribution/development/changelog/agent documents. For all 71 GitHub-backed entries, inspected up to 100 recent commits and searched indexed repository commit history for Claude, Codex, Copilot, AI-assisted and vibe-coding references; older matches and promising implementation/PR histories were read in context. README/document searches also covered ChatGPT/GPT, Cursor, generated-code and coding-agent concepts. Search matches were leads, including false matches to runtime providers, human names and branch names.

Spade and Surfer were checked through their canonical GitLab READMEs, changelogs and recent histories. ATLAS was checked against the versioned author paper; ngspice against official release/development sources. Related UHDM and RTLTracer materials were checked separately from their catalog entries’ activity repositories. Maintainer posts/articles and targeted web searches supplied or tested promising leads. Linked evidence was fetched from public project sources; repository document links are revision-pinned where available. Search indexes, documentation coverage and public disclosures are incomplete, especially for imported histories. This is a reproducible classification review, not a complete authorship census.

No runtime stage confusion was found that required a correction. No stage boolean, activity snapshot, project membership, functional description, visual style, Golden fact, Article or export is changed by this audit.

## Existing-label decisions and the new label

### KEEP — Ngspice + OpenVAF Enhancements — A

The owner, **Dr. Meisam Bahadori**, expressly describes this repository as using Claude Code to enhance ngspice and OpenVAF. This is a coherent, separately cataloged enhancement effort with maintained implementation, example suites and feature write-ups. ## Consistency and outcome

**8 previous labels → 6 KEEP + 2 REMOVE; 1 ADD → 7 final labels.** Final Analog: **CircuitRubric, Ngspice + OpenVAF Enhancements**. Final Digital: **iverilog-uvm, uhdm2rtlil, vivado_mcp, WHAT, xezim**. Every final label is **Tier A**; no Tier-B exception is promoted.

Read together, the final set makes the same qualitative claim: the project directly documents AI-assisted software construction as a notable fact about its creation or its defining enhancement effort. It does not claim that all inherited code was AI-written, that AI operates in the design workflow, or that outputs are correct.

The unlabeled B cases include Veryl and vitamin, but also ARCS, EVAS, vcli, virtuoso-bridge-lite, OpenADA, sv-elab and the other bounded campaigns in the matrix. Their meaningful contributions are recorded without silently turning co-authorship counts, an intended agent workflow, a port, or a useful feature into whole-project provenance. Functional descriptions already explain the tools without depending on the badge, so none requires rewriting. Veryl/vitamin provenance notes are corrected; CircuitRubric gains its explicit disclosure.

Schema and rendering regressions exercise true/absent provenance and all independent runtime-AI combinations, rejecting strength/tier fields. Project-specific provenance decisions belong in this review record; do not hardcode the final set in UI tests. Inventory-driven smoke tests verify actual authored badges in both catalogs. Local validation results are recorded in the domain implementation notes; deployment and production verification are reported at delivery.
