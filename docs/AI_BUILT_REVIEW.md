This review covers **all 75 current projects: 35 Analog and 40 Digital**, starting from `caf8f24a3626cdbe7cfdc8c5ac85742c6cb2d2cc` on `main`. The starting data contained **7 AI-BUILT labels** (2 Analog, 5 Digital). No project is added or removed. The complete matrix below was authored and checked against the inventory **before applying any catalog classification changes**.

The previous [2026-09-06 binary audit](AI_BUILT_REVIEW_2026-09-06.md) remains distinguishable as history. Its A/B/C/D research tiers are not mapped to public labels. This review supersedes its policy and all earlier provenance decisions in the domain notes and Scope review, while preserving useful evidence and unrelated requirements.

## Shared policy

These labels describe **development of the software**, independently of runtime AI in a user’s design workflow:

- **AI-ASSISTED**: strong direct evidence of substantial AI-assisted implementation of a meaningful feature, subsystem or implementation campaign within the current project, without characterizing the project’s whole or defining-core construction.
- **AI-BUILT**: strong direct evidence that AI played a major implementation role across the project, or in a defining core that reasonably characterizes its development provenance.
- **No label**: qualifying evidence is absent, inaccessible, ambiguous or incidental. This does not assert exclusively human development.

Both displayed categories require strong direct evidence. Their difference is **contribution scope and significance**, not confidence, software quality, maturity, runtime autonomy or an estimated percentage of generated code. AI-ASSISTED is never a fallback for weak AI-BUILT evidence. AI-BUILT does not mean every file was generated or that humans supplied no direction.

A creation account may establish a defining-core role. A bounded implementation decision requires an identifiable contribution, attributable implementation material and evidence that it remains meaningful in the current project. A credited commit is useful only after reading its actual code changes, purpose and integration; credit counts, large test/data diffs and broad commit-message claims are not sufficient. File size is not a threshold. Substantial new backend, analysis, orchestration and runtime-storage subsystems differ from a thin control over an existing algorithm, an isolated correctness repair or ordinary build maintenance.

Runtime AI, MCP/agent interfaces, AI research subject matter, generated test inputs/examples/docs, ordinary completion, small isolated fixes, instruction files, bot PRs, a handful of co-author credits and casual assistant mentions do not qualify on their own. Refactoring must establish a substantial implemented contribution, not just moved lines. Forks, ports and enhancements are assessed as the named catalog project; attribution does not spread to upstream dependencies or to an unattributed rewrite.

## Method and evidence limits

Reused the previous full-inventory investigation (canonical documentation, recent and indexed older implementation histories, maintainer accounts and companion repositories), reopened its cited primary sources, and inspected additional implementation diffs where the new threshold required it. Rechecked default-branch heads and retained code paths for candidate labels. The Veryl maintainer article and xezim creation account were reread in context. For OpenROAD-MCP, current TypeScript code was checked after the Python implementation’s removal; the permission model remains, but AI authorship is not inferred for the port.

Each labeled row identifies what AI helped implement, why it is substantial and why the selected scope applies. The separate “Evidence limits” column records attribution uncertainty without turning it into a public confidence field. A no-label decision is bounded by public disclosures and accessible history, not a census of private tool use. Source links are primary and revision-pinned where practical. Spade’s toolchain source access remains limited; no human-only claim is derived from a contribution policy. Documentation-generation disclosures are kept distinct from implementation evidence.

**Review date: 2026-09-07 (Asia/Tokyo).** This is a provenance review date, not project activity. Existing activity snapshots, dates, chronological bands, functional Scope stages, runtime AI booleans, descriptions, Golden facts, Articles and export semantics are preserved.

- **CircuitRubric → NO LABEL:** the disclosure explicitly includes tooling as well as corpus drafting, so it must not be described as corpus-only. However, it does not identify a substantial AI-implemented component or establish a major implementation role. The initial code release cannot supply missing attribution; the code guide separately says it was generated from code. Neither displayed label is justified by the remaining uncertainty.
- **vitamin → AI-ASSISTED:** the package-storage/import/initialization campaign provides concrete implementation evidence under the new definition. The old concern about whole-simulator attribution remains; sustained credits and agent instructions are not converted into AI-BUILT.
- **Dynamatic → AI-ASSISTED:** the new instrumentation subsystem qualifies. Its LSQ refactor does not supply AI implementation evidence: the author explicitly says it was handwritten and Claude-reviewed.
- **ALIGN, EVAS, Magic, OpenVAF-Reloaded, OpenROAD and Surelog/UHDM → NO LABEL:** old B summaries do not automatically qualify. Reading code separated specifications, tests, build plumbing and small repairs from substantial implemented subsystems.

## Data and maintenance contract

`scope.aiDevelopment` is a single optional enum: `assisted` or `built`; omission means no public badge. Legacy `aiBuilt` is rejected, with no compatibility conversion and no second classification field. Each present enum requires `developmentEvidence` containing one or two factual sentences in `summary`, one to three distinct existing source IDs in `sources`, and its own calendar `reviewedAt`. Evidence without a classification, a classification without evidence, invalid IDs, duplicate references and unknown fields fail validation. The provenance review date is independent of activity snapshots; do not refresh activity just to change a badge.

Runtime AI stays in each functional stage’s `{ ai: boolean }`. Either provenance enum can accompany either runtime boolean, and provenance cannot satisfy the required functional-stage presence. No public tiers, scores, percentages or human-only labels are added.

The shared index renders exactly one final provenance badge after the stages, with a small extra gap: AI-ASSISTED outlined in muted red, AI-BUILT filled in the same color family. Activating the badge opens an inline “Development provenance” explanation and primary links. Search indexes the displayed badge text along with existing public name/description/stage text; it does not index hidden research or source URLs. Stage filtering stays independent. Without JavaScript, explanations and source links remain readable in static HTML.
